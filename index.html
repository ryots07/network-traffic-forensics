01 · Overview

Why this project exists.

Network traffic forensics is about more than collecting packets. The investigator has to understand the communication in context, isolate relevant protocols, correlate traffic with known activity and decide what the available evidence actually supports.

Problem

Legitimate traffic can look unfamiliar.

Common protocols, public services and ordinary connection behaviour can appear alongside traffic that deserves further investigation.

Aim

Investigate the selected interface.

Capture traffic on eth0 and determine whether the reviewed packets contain observable characteristics of suspicious or malicious behaviour.

Approach

Do not force a malicious finding.

Where evidence does not demonstrate malicious or abnormal behaviour, that result is retained and qualified rather than exaggerated.

02 · Objectives

What the practical set out to do.

The investigation was built around capture, filtering, controlled traffic generation, correlation and assessment.

01–03

Capture & isolate

Capture live traffic through eth0, then apply protocol-specific Wireshark filters and generate controlled DNS activity with nslookup.

04–06

Correlate & inspect

Generate web traffic with curl https://example.com/, inspect TCP/TLS communication and examine SYN/SYN-ACK states.

07–09

Cross-check & assess

Check retransmissions, use TCPdump for command-line capture, review Protocol Hierarchy and assess the evidence for suspicious characteristics.

03 · Scope & Tools

The working environment.

The project is limited to the traffic captured during the practical sessions represented in the supplied evidence. It is not a full enterprise assessment or continuous monitoring exercise.

06 · Discussion

What the evidence means.

A display filter only reports what exists inside the capture being filtered. A zero result is not automatically a security finding. The practical repeatedly used controlled activity to make the traffic observable and then correlated the result with the action performed.

Negative filter results

  • The initial DNS filter returned 0 displayed packets from an 18-packet capture.
  • The initial TCP filter returned 0 displayed packets from a 131-packet capture.
  • The http filter returned 0 packets from the 68-packet TCP capture.
  • tcp.analysis.retransmission returned 0 packets in the supplied TCP capture.

Correlation

  • Four nslookup commands created known DNS activity.
  • The later DNS capture contained 131 packets, with 16 displayed as DNS.
  • curl https://example.com/ created known web activity.
  • The later TCP capture contained 68 packets, with 31 displayed as TCP and TLS 1.3 traffic including SNI example.com.
07 · Results

What was actually found.

The evidence supports several concrete observations, while the security conclusion remains deliberately limited to the reviewed captures.

● SECURITY ASSESSMENT

No confirmed malicious or clearly abnormal activity was identified.

The observed DNS traffic corresponds to the deliberate nslookup activity. The TLS traffic to port 443 and SNI example.com corresponds to the explicit curl https://example.com/ request. The SYN/SYN-ACK observations are consistent with TCP connection establishment, and no retransmissions were flagged in the supplied TCP capture.

This conclusion applies only to the traffic captured and reviewed during the practical. It does not establish that the wider host or network was completely secure.

08 · IOCs

What would require further investigation?

Indicators of compromise are context-dependent. A packet, public address or port number is not automatically malicious simply because it appears in a capture.

Destinations

Unexpected endpoints

Unexplained or repeatedly contacted destinations that cannot be correlated with the activity being performed.

DNS

Unusual queries

Unexpected domains, unusual naming patterns or abnormal query frequency that warrant deeper review.

Connections

Unexpected services

Unusual ports, repeated failed connections or traffic patterns inconsistent with expected application behaviour.

Traffic

Unexplained behaviour

Protocols or data transfers that cannot be explained by a known user, process, application or experiment.

Analysis

Potential C2 / tunnelling

Evidence suggesting command-and-control communication, tunnelling or unexplained transfer would justify additional investigation.

This practical

No confirmed IOC

The supplied evidence does not establish any of these characteristics as a confirmed malicious indicator.

10 · Conclusion

From packet capture to practical understanding.

The project demonstrated a practical workflow for network traffic forensics and suspicious activity assessment using Kali Linux, Wireshark and TCPdump.

The investigation began with a baseline packet capture on eth0, where NTP, SSDP, ARP and ICMPv6 traffic were observed. An initial DNS filter returned zero packets, after which controlled DNS queries were generated using nslookup for google.com, youtube.com, steampowered.com and wikipedia.org. The subsequent capture contained 131 packets, with 16 displayed as DNS traffic.

The initial TCP filter also returned zero packets in the earlier capture. TCP traffic was then generated using curl https://example.com/. A subsequent 68-packet capture contained 31 displayed TCP packets, including TLS 1.3 communication over port 443 and a Client Hello containing SNI=example.com.

TCP SYN and SYN-ACK analysis identified two initial SYN packets and two SYN-ACK packets. The retransmission filter returned zero packets. TCPdump successfully captured 20 packets, with 20 received by the filter and 0 dropped by the kernel. A Protocol Hierarchy review of a separate 12-packet capture showed SSDP, NTP and ARP traffic.

Based on the supplied evidence, no confirmed malicious or clearly abnormal activity was identified. The practical therefore demonstrates the workflow of Capture → Filter → Inspect → Correlate → Assess → Report, while keeping the final conclusion limited to the traffic actually visible in the supplied evidence.
